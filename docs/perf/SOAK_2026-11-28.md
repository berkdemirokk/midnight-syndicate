# Soak measurement, 2026-11-28 (wp/soak)

Long-session stability on the Windows dev PC (NVIDIA RTX 5060 Ti 8 GB, Godot 4.7.2). Desktop numbers only, not phone numbers.
No gameplay change. Harness: `game/devtools/soak.gd` (run through `game/devtools/soak_boot.tscn`).
It runs the real race scene (`race/race_scene.tscn`) back to back in one process: istanbul_bogaz, grid 6, 2 laps, night, autopilot player (noctra_tayfun, skill 0.97), no traffic, no rival mix.

## Headless: 10 consecutive races in one process

Raw: `evidence/soak/headless_10races_2026-11-28.json`. Command: `--headless --audio-driver Dummy --fixed-fps 60`, `--mode=sim --races=10`.

- 10 of 10 races finished, none timed out. Race time 116.3 to 131.6 s (sim). Player finish positions 2 to 6.
- Memory, measured 30 frames after `queue_free` of the scene:

| Counter | Before race 1 | After race 1 | After race 10 | Change, races 1 to 10 after free |
|---|---|---|---|---|
| Static memory (MB) | 69.38 | 198.95 | 199.50 | +0.55 (one dip of 0.02, otherwise rising) |
| Objects | 1626 | 2032 | 2032 | flat (range 2030 to 2036) |
| Nodes | 9 | 19 | 19 | flat |
| Orphan nodes | 0 | 0 | 0 | flat |
| Resources | 98 | 201 | 201 | flat |

- The first race leaves a one-time resident step: about +130 MB static, +103 resources, +406 objects and +10 nodes (9 to 19) that stay after the scene is freed, then stay flat. Resources that stay loaded after the first race (a resource cache) fit this; the exact owners were not traced.

- Live race (at finish, scene still up): about 10,225 to 10,231 objects, about 353.6 to 354.2 MB static. The scene is fully released each time.
- Flags from the monotonic check: none for objects, nodes, orphan nodes or resources. Static memory rose 0.55 MB over races 2 to 10 (after free), about 0.06 MB per race. That is within what a 10-race sample can show, so it is not called a leak.

## Rendered: 8 races under the GPU lock (Istanbul Bogaz, night, preset high)

Raw: `evidence/soak/render_bogaz_night_high_2026-11-28.json`. Command: `gpu_run.py` wrapping `--audio-driver Dummy --resolution 1920x1080 --position 20000,0`, `--mode=render --minutes=16`.

Window and length: the run stopped starting new races at 16 min (960 s). The last race ended at 1045.5 s wall, about 17.4 min in total. The target was 20 minutes, but `gpu_run.py` kills the process at 20 minutes (hard timeout), so a 20-minute window with the last race allowed to finish could not fit in one lock hold. Eight full races, none timed out. Renderer: mobile method, adapter NVIDIA GeForce RTX 5060 Ti. The screen reports 180 Hz. Frame rate is capped at 60 by the project setting `run/max_fps=60` (`game/project.godot` line 12), not by vsync.

- Video memory is flat at about 753.5 MB from minute 3 onward.

Some minutes dip by about 1 MB, so the trend is not strictly monotonic.

Per race, measured 30 frames after `queue_free` (races 1 to 8):

- Static MB: 662.39, 662.61, 663.01, 663.22, 663.47, 663.77, 663.81, 664.06. Non-decreasing, +1.67 MB over races 2 to 8, about 0.24 MB per race. (Before race 1: 605.41 MB, resources 98.)
- Objects 1940 to 1942, nodes 19, resources 200 then 201 from race 2 on, video 587.86 MB. All flat.

## Verdict

- Frame time does not drift in 17 minutes of desktop rendering. Every minute is at the 60 fps cap (`max_fps=60`), with about 2 to 3 spikes over 33 ms at each race start.
- Video memory does not grow after the first race.
- Object, node and resource counts stay flat in both the headless and the rendered runs. The first race leaves a one-time resident step (about +130 MB headless, +57 MB rendered, about +100 resources), then counts stay flat. After that, static memory creeps up: about 0.06 MB per race headless (races 2 to 10), about 0.24 MB per race rendered (races 2 to 8), after the scene is freed. Neither run shows monotonic growth in the object counts.
- No per-race leak is confirmed; the "no leak" finding covers the baseline after the first race. The one drift candidate is static memory, which rises by a fraction of a megabyte per race. The code that creates it was not identified. The first-race resource step (+103 resources that stay) points to resources kept loaded after the first race, but their owners were not traced. This package does not fix anything.

## Limits

- Desktop numbers only. Not phone numbers.
- The rendered run is 16 minutes of racing plus the final race, not 20, because of the 20-minute hard timeout in `gpu_run.py`.
- The project setting `run/max_fps=60` caps frame time at 16.67 ms, so headroom cannot be read from this run. A headroom run needs `Engine.max_fps = 0` (as `game/devtools/perf_probe.gd` does) plus vsync off; vsync off alone would not lift the cap.
- Video memory is sampled from `RENDERING_INFO_VIDEO_MEM_USED`. It is a driver figure, not a full accounting.
- A first rendered attempt with an 18-minute window had a bucketing bug in the per-minute frame stats (packed-array buckets were copies, so the array came out empty). It was fixed and the run was repeated. The reported run is the repeat. The first attempt's memory baseline was about 200 MB higher (static 864 MB after race 1, against 662 MB in the repeat), and its ninth race was cut at the window grace limit. Its object, node, resource and video counts matched the repeat, and its static memory also rose slowly (about 2 MB over nine races). That attempt's file was overwritten by the repeat.
- A headless run of the harness ends with `WARNING: 4 ObjectDB instances were leaked at exit` and `ERROR: 2 resources still in use at exit` (reproduced in lead review with `--races=1`). These are exit-time warnings, not per-race growth, and were not traced (`--verbose` would name them). The full test suite prints a similar exit message.
- No screenshots were taken. This is a timing and memory run, not visual evidence.
